Wie es technisch zusammenhängt

Architektur

Stargate ist ein Stack aus vier Anwendungsservices plus Infrastruktur. Die Mail läuft in drei Sprüngen durch, der zweite enthält die kryptografische Arbeit.

Mail-Flow · Eingehende Mail

Vom externen Sender bis ins Exchange-Postfach des Empfängers. Jeder Pfeil ist ein echter Netzwerk-Hop, jeder Block ein Container.

1Inbound — externe Mail trifft auf Port 25. Stalwart entscheidet anhand von content_filter, die Mail zunächst an MXEngine zur Verarbeitung weiterzuleiten. 2Processing — MXEngine erledigt die eigentliche Arbeit: Policy-Lookup (wie soll diese Mail behandelt werden?), S/MIME-Signatur, Seal-Erzeugung. Schlüssel kommen via smimekeys-client aus Vault. 3Reinjection — Verarbeitete Mail geht zurück an Stalwart auf Port 10026 (internes Listener). 4Delivery — Stalwart liefert via MX-Lookup an den Ziel-Mailserver, oder über ein im Dashboard (/mail) konfiguriertes Relay (gemeinsam oder per Domain).

WireGuard · Appliance-zu-Appliance

Jede Stargate-Instanz ist ein eigener WireGuard-Peer. Die öffentliche IP des Servers dient als eindeutige Tunnel-Adresse — so braucht es keinen zentralen Koordinator für WG-IPs.

Der kritische manuelle Schritt

Nach dem ersten Install hat euer Appliance zwar einen Public Key generiert — auf der HIN-Seite ist er aber noch nicht registriert. Bis das nicht passiert, kommt kein Handshake zustande und damit auch keine Zertifikatsausstellung. Siehe Troubleshoot für die exakten Symptome.

Die echten Weichen

Entscheidungen

Sieben Stellen, an denen man sich wirklich entscheiden muss — mit ehrlichen Trade-offs statt "Best Practice"-Parolen.

Entscheidung 01

Mail-Routing-Strategie

Wie findet die ausgehende Mail ihr Ziel — nach der Verarbeitung durch MXEngine? Drei sich ausschliessende Wege.

MX-basiert Empfohlen für Einzel- bis Multi-Domain mit eigener Infra
Stalwart liefert nach DNS-MX-Lookup pro Domain direkt an den Ziel-MX (Default). Pro: Keine Relay-Config nötig — ihr steuert im DNS. Contra: Setzt voraus, dass die Ziel-MX die Appliance-IP akzeptieren (Reputation/SPF beachten).
Smart-Host Ein Ziel für alle
Alle Domains gehen über ein gemeinsames Relay-Ziel (z.B. zurück ins eigene M365/Exchange-Tenant). Konfiguration im Dashboard auf /mail. Pro: Einfach, gute Sender-Reputation über Microsoft. Contra: Kein Per-Domain-Routing.
Per-Domain-Relay Service-Provider-Fall
Jede Domain wird auf ihr eigenes Relay-Ziel (eigenes M365/Exchange-Inbound) gemappt — im Dashboard auf /mail. mtaconf übernimmt die Konfiguration zur Laufzeit an Stalwart (kein Container-Neustart). Pro: Sauber für viele Domains mit unterschiedlichen Zielen. Contra: Pflege je Domain.
Entscheidung 02

Deployment-Plattform

VM-Image, bestehender Linux-Host oder K8s — alle drei Wege führen zum identischen Stack, nur der Aufwand unterscheidet sich.

VM-Image (Azure · VMware · Proxmox · Hyper-V)
Fertig vorbereitetes Alma-Linux-Image mit allen Deps. Pro: Schnell, reproduzierbar, keine OS-Pflege nötig. Contra: Ihr müsst die Plattform-spezifische Import-Zeremonie mitgehen.
Bestehender Linux-Host (Docker-Install)
Repo klonen, install.sh ausführen. Docker wird bei Bedarf installiert. Pro: Volle Kontrolle über Host-OS, Patch-Zyklus im eigenen Standard. Contra: Ihr seid für OS-Hardening verantwortlich.
Kubernetes (Helm)
Helm-Chart für bestehende Cluster. Pro: Passt zu bestehendem K8s-Betrieb. Contra: WireGuard-Host-Networking und statische IP brauchen erhöhte Privilegien — nicht in jedem Managed-K8s möglich. Dokumentation bei HIN anfordern.
Entscheidung 03

Phase · Alpha / Beta / Produktion

Bestimmt CA-Endpunkt, Peer-Ziel und Erwartungshaltung.

Alpha aktuell
Verbindung zur HIN Test CA (hintest.ch). CSR wird automatisch signiert. Keine Produktions-Mails. Test-Domain verwenden. Häufige Updates zu erwarten.
Beta
Noch Test-CA, aber echter Traffic-Test nach separater Freigabe möglich. Zeitpunkt wird separat kommuniziert.
Produktion Termin verschoben
Verbindung zur HIN Produktions-CA. Reguläre S/MIME-Zertifikate mit 1 Jahr Gültigkeit. Peer muss manuell bei HIN registriert werden. Hinweis: Der ursprünglich für 18.05.2026 geplante Rollout der PRD-Images wurde von HIN verschoben — das Engineering-Team arbeitet aktuell an offenen Punkten. Neuer Termin wird kommuniziert, sobald die PRD-Images verfügbar sind.
Entscheidung 04

Exchange-Integrations-Pattern

Beide Pattern sind möglich und funktionieren — der Unterschied ist, ob Stargate der primäre MX ist oder die Mail via Transport-Rule umgeleitet wird.

Pattern A Stargate als primärer MX
Stargate MX 15, Exchange MX 20. Internet → Stargate → Exchange. Empfohlen: Die inbound S/MIME-Verarbeitung passiert automatisch für alle Mails. Transport-Rule nur für outbound nötig.
Pattern B · Exchange als primärer MX
Exchange bleibt der Haupt-MX, Transport-Rule schickt Mails je nach Kriterium über Stargate. Sinnvoll wenn ihr nur einen Teil der Mails durch Stargate routen wollt. Mehr Konfiguration.
Beides: Outbound-Transport-Rule mit IP-Ausnahme
Kritisch: In beiden Pattern muss die Transport-Rule "Except if sender IP is <STARGATE_IP>" gesetzt sein — sonst Mail-Loop.
Entscheidung 05

WireGuard-Transport · TCP vs. UDP

WireGuard ist ursprünglich UDP-only, HIN benutzt eine Variante die TCP kann — das erleichtert Firewall-Passage.

TCP Default
Funktioniert durch die meisten Firewalls, auch mit tiefer Packet-Inspection. Tipp: So starten und erst wechseln, wenn konkret Probleme auftreten.
UDP
Native WireGuard-Performance. Wann sinnvoll: Bei stateful Firewalls die langlebige TCP-Verbindungen aggressiv droppen, oder wenn Latenz entscheidend ist (bei S/MIME zwischen Institutionen kaum relevant).
Entscheidung 06

Zentrale Log-Zusendung

Ob Logs an HINs Loki gesendet werden — oder ausschliesslich lokal bleiben.

Loki aktiviert Default
Alloy schickt Logs der 4 Anwendungs-Container an loki.infra.vereign-cdn.com. Pro: HIN-Support kann bei Problemen direkt mitsehen. Contra: Eure Appliance-IP muss bei HIN in der Loki-Ingress-Whitelist stehen.
Loki deaktiviert
LOKI_URL="" setzen und Alloy-Service in docker-compose.yml entfernen/kommentieren. Pro: Logs bleiben strikt lokal. Contra: Ihr müsst für HIN-Support Logs manuell bereitstellen (docker compose logs).
Entscheidung 07

Backup-Strategie

Das eingebaute Backup deckt den Appliance ab — aber wohin muss eure Infrastruktur-Policy lösen.

Eingebauter Cron-Backup
Läuft täglich 02:00 lokal via ./scripts/backup.sh. Enthält PG-Dump, Vault-Keys, customer-config, Zertifikate. Retention 7 Tage lokal.
Externe Replikation · Pflicht
Kritisch: Das Backup-Verzeichnis muss täglich extern repliziert werden (S3, Azure Blob, Veeam, rsync nach Remote-Storage — egal was). Bei Totalverlust ohne externes Backup ist der WG-Private-Key weg und ihr braucht neue Peer-Registrierung bei HIN.
Snapshot-basiert (zusätzlich)
Auf VM-Ebene regelmäßige Snapshots (Azure, vSphere, Proxmox, Hyper-V). Deckt zusätzlich das Host-FS ab. Für schnelle Recovery-Szenarien (in 15 Min. wieder up) oft bequemer als dateibasierter Restore.

Architektur & Skalierung

Kann ich mehrere Stargate-Instanzen clustern für Hochverfügbarkeit?

Update Juni 2026 Geplant ab September 2026. Laut HIN/Vereign sind Redundanz- und Clustering-Optionen — inklusive SMTP-Load-Balancing und Active-Active-Failover — geplant und sollen ab September verfügbar sein. Eine der primär diskutierten Optionen ist ein Load Balancer vor dem Cluster, vergleichbar mit dem heutigen HIN-MGW-Cluster-Setup. Bis dahin gilt das Folgende.

Aktueller Stand: Ein natives Cluster gibt es noch nicht. Jede Stargate-Instanz hat eine eigene Datenbank, ein eigenes Vault, ein eigenes WireGuard-Keypair und ein eigenes S/MIME-Zertifikat. Zwei Instanzen parallel teilen keinen State.

Was bis dahin pragmatisch funktioniert: Zwei unabhängige Appliances mit unterschiedlichen MX-Prioritäten (primary + backup). Beide müssten separat bei HIN als Peers registriert sein. Mail, die während des Ausfalls des primären Systems ankommt, würde an den Backup-MX zugestellt. Das ist aber nicht offiziell getestet und sollte nur nach Absprache mit HIN gemacht werden.

Hinweis zum SMTP-Loadbalancer: Innerhalb von Stargate nimmt der MTA-Microservice eingehende Nachrichten an und leitet sie an den nächsten Relay-Host weiter. Load Balancing in einer Active-Active-Konfiguration wird derzeit evaluiert. Die heutige Funktion „SMTP Loadbalancer ab 2 pending E-Mails" ist bis September nicht nativ verfügbar — bei hohem, gleichzeitigem Mailaufkommen (mehrere tausend Mails) frühzeitig mit HIN abstimmen.

Kann ein einziger Appliance mehrere Kunden bedienen (Multi-Tenant)?

Aktuell nein. Die Architektur ist 1:1 — ein WireGuard-Keypair, ein S/MIME-Zertifikat, eine Kundenidentität pro Appliance.

Das ist ein bekanntes Problem für Service Provider: Ein Anbieter mit 30 Kunden auf einem alten MGW (3 CPU, 6 GB RAM) bräuchte nach aktueller Architektur 30 separate Appliances — ca. 120 CPUs, 240 GB RAM, 30 öffentliche IPs. HIN evaluiert dieses Szenario. Kunden mit diesem Use-Case sollten aktiv nachfragen.

Kann ich Stargate in Kubernetes betreiben?

Ja, Helm-Charts sind vorhanden. Die Doku dazu (helm-deploy.md) ist aktuell noch knapp — für Kubernetes-Deployment direkt bei HIN anfordern.

Zu beachten: Der Appliance braucht eine statische öffentliche IP für WireGuard. In Managed-K8s (AKS, EKS, GKE) ist das oft tricky — Host-Network oder LoadBalancer mit statischer IP nötig. Bei Cluster-internen Deployments auch UDP für WireGuard unterstützen.

Welche Cloud-Plattformen werden unterstützt?

Fertige VM-Images gibt es für Azure, VMware/ESXi, Proxmox, Hyper-V — alle auf Basis Alma Linux. AWS und GCP haben keine fertigen Images, funktionieren aber problemlos mit der Docker-Installation auf einem regulären Linux-VM.

Unterstützte Linux-Distributionen für Docker-Install: RHEL 8/9/10, Alma Linux, Rocky Linux, CentOS Stream, Ubuntu 22/24, Debian 11/12/13.

Warum ist S3-Storage drin? Kann ich den an externes S3 (AWS, Azure Blob) anbinden?

MXEngine speichert Message-Bodies und Attachments in Object-Storage. Intern läuft dafür MinIO im selben Docker-Stack — also nicht zentral, sondern pro Appliance lokal.

Aktuell ist das MinIO-Target nicht über Config-Keys austauschbar. Technisch ist MinIO voll S3-API-kompatibel, aber die Services zeigen fest auf die lokale Instanz. Wer externes S3 haben will, müsste das in docker-compose.yml entsprechend ändern und dort AWS-Endpunkte eintragen — wird aber nicht offiziell supportet.

Wie performt der Appliance? Welche Last hält er aus?

4 CPU / 8 GB / 30 GB ist die empfohlene Dimensionierung; das dokumentierte Minimum liegt bei 2 CPU / 4 GB / 20 GB. Konkrete Benchmark-Zahlen (Mails/Sekunde) gibt HIN aktuell nicht öffentlich aus. Pragmatische Richtschnur: Für eine mittelgrosse Klinik mit < 10.000 Mails/Tag ist die Referenz-Dimensionierung mehr als ausreichend. Bei höherem Volumen vertikal skalieren (mehr CPU/RAM) — horizontales Scaling ist wie oben beschrieben nicht vorgesehen.

Was sind die wesentlichen Unterschiede zum Seppmail-basierten Legacy-MGW?

Stargate bringt technisch, funktional und sicherheitsseitig deutliche Änderungen mit. Kern: direkter, verschlüsselter Peer-to-Peer-Transport über einen sicheren Tunnel (schützt sämtliche Metadaten) statt klassischem SMTP-Routing. Zusätzlich entsteht Infrastruktur für Organisations-Wallets/-Zertifikate und perspektivisch ein schweizweiter strukturierter Datenaustausch zwischen Klinikinformationssystemen (erste Piloten erwartet Q3/Q4 2026).

Welcher Mail-Transport-Agent (MTA) wird eingesetzt — und wo liegen die Config-Files?

Stargate verwendet als MTA Stalwart (stalw.art) — einen modernen, rootless betreibbaren Mailserver. Das gilt für alle Deployment-Wege (VM-Image, Docker und später Cluster); Postfix wird nicht mehr eingesetzt.

Konfiguration: Domains und Relay-Einstellungen werden nicht in statischen Config-Files gepflegt, sondern zur Laufzeit über das Dashboard auf /mail gesetzt. Diese Eingaben gehen an den mtaconf-Daemon (REST-API), der Stalwart ohne Container-Neustart neu konfiguriert (Reloads werden über NATS ausgelöst).

Hintergrund: Stalwart ersetzt das früher eingesetzte Postfix — u.a. wegen des rootless-Betriebs (Postfix braucht Root für die Subprozess-Kontrolle, was im Cluster nicht erlaubt ist) und der nativ integrierten Mail-Security-Funktionen (SPF/DKIM/DMARC/ARC/MTA-STS/DANE).

Security & Compliance

Welche Verschlüsselung wird verwendet?

RSA für die S/MIME-Mail-Inhalte. ChaCha20-Poly1305 für den WireGuard-Tunnel (Standard-Chiffre von WireGuard).

Kann der Appliance air-gapped (ohne Internet) laufen?

Nein. Das ist ein wichtiger Unterschied zum Legacy-MGW, der das konnte. Der neue Appliance braucht Internetzugang, um:

  • Docker-Images von hub.docker.com zu ziehen
  • den WireGuard-Tunnel zur HIN CA aufzubauen
  • optional Logs an Loki zu senden

Kunden mit Hard-Offline-Policy müssen ihre Architektur anpassen — z.B. mit einem gewhitelisteten Outbound-Proxy.

Wie wird der S/MIME-Private-Key geschützt?

Gespeichert in HashiCorp Vault (KV-v2) auf dem Appliance selbst. Vault wird bei jedem Container-Restart automatisch versiegelt — start.sh entsiegelt ihn mit den lokalen Unseal-Keys aus secrets/vault-keys.json. Der Key verlässt die Appliance nie im Klartext.

Kritisch: secrets/vault-keys.json muss extern gesichert werden — geht diese Datei verloren, ist das Vault für immer versiegelt.

Telemetrie — werden Daten an HIN oder Dritte geschickt?

Nein — ausser dem, was ihr explizit konfiguriert:

  • Logs an Loki (falls LOKI_URL gesetzt, default aktiv) — abschaltbar
  • WireGuard-Traffic zur HIN CA — das ist der Kernzweck, kein "Telemetrie" im klassischen Sinne
  • Keine separate Anonymous-Telemetry, keine Nutzungsstatistiken
Wird der Appliance penetriert getestet?

Ja, durch HIN in der zweiten Hälfte April 2026 — vor dem Produktions-Rollout.

Wurde die modifizierte WireGuard-Implementierung (Application-Layer) auditiert?

Offene Frage Stargate verwendet eine WireGuard-Variante, die TCP ergänzt — das ist nicht das native Protokoll. Ob diese Modifikation formal auditiert wurde, ist nicht öffentlich dokumentiert. Für Kunden mit hohen Security-Anforderungen: direkt bei HIN anfragen.

Wo werden die Daten verarbeitet?

Ausschliesslich auf dem kundeneigenen Appliance. Kein Upload von Mail-Inhalten irgendwohin. Einzige Ausnahme: Logs an Loki (falls aktiviert) — diese enthalten keine Mail-Bodies, sondern nur Service-Logs. Loki wird von HIN/Vereign betrieben; die exakte Rechtsgebietszugehörigkeit der Loki-Infrastruktur sollte bei HIN erfragt werden.

Zertifizierung · ISO 27001?

HIN hält ISO 27001. Für Stargate spezifisch (als Produkt) gibt es aktuell keine separate Zertifizierung — der Appliance läuft beim Kunden, die ISO-27001-Zertifizierung bezieht sich auf HIN selbst als Organisation.

Funktioniert die Anbindung an Microsoft Azure / Entra ID (z.B. Guest Accounts)?

Stargate enthält Keycloak als Identity- und Access-Management-Layer. Keycloak lässt sich so konfigurieren, dass es mit bestehenden Azure-AD-/Entra-ID-Realms oder anderen externen Identity Providern föderiert (Guest-Account- bzw. IdP-Integration für Authentifizierung).

Da der konkrete Use-Case die richtige Keycloak-Konfiguration bestimmt: bei der Anbindung von Azure-Guest-Accounts den genauen Anwendungsfall an HIN/Vereign schildern, damit die passende Föderationskonfiguration empfohlen werden kann. (Hinweis: Im Legacy-MGW war dieser Fall teils nicht lösbar — die Keycloak-Schicht ist hier der neue Lösungsweg.)

Zertifikate & CA

Werden externe CAs wie Let's Encrypt akzeptiert?

Nein, und auch nicht nötig. S/MIME-Zertifikate werden ausschliesslich von der HIN CA ausgestellt — und zwar über den WireGuard-Tunnel. Diese Zertifikate dienen nur der Kommunikation innerhalb der HIN-Community.

Für SMTP-TLS gilt: Wenn ihr ausgehende Mail über das eigene M365/Exchange-Tenant zurückrelayed (empfohlen für die Sender-Reputation), verlangt der Exchange-Inbound-Connector ein gültiges, öffentlich vertrauenswürdiges TLS-Zertifikat — ein selbst-signiertes Zertifikat wird dort abgelehnt. Ein Let's-Encrypt-Zertifikat genügt und lässt sich über die Web-UI hochladen (siehe „Wie lade ich ein eigenes SSL-Zertifikat hoch …?").

Wie lange sind die Zertifikate gültig?

1 Jahr ab Ausstellung. Erneuerung/Rotation erfolgt über das Dashboard auf /onboarding (ersetzt das frühere onboard.sh --regenerate-cert). Empfehlung: Monitoring-Alert auf "Ablauf < 30 Tage" setzen, gute 4 Wochen Puffer einplanen.

Was passiert, wenn das Zertifikat abgelaufen ist?

S/MIME-Signierung und -Entschlüsselung schlägt fehl. Regulärer Mail-Transport an Nicht-HIN-Empfänger läuft weiter, aber HIN-interne Kommunikation ist unterbrochen, bis ein neues Zertifikat ausgestellt ist.

Neu ausstellen über das Dashboard auf /onboarding — geht in wenigen Sekunden, solange der WireGuard-Tunnel steht.

Kann ich Zertifikate im Voraus erneuern?

Ja, jederzeit. Über das Dashboard auf /onboarding wird ein neuer CSR erzeugt, durch den Tunnel geschickt und das bestehende Zertifikat ersetzt. Kein Downtime, sofern der Tunnel steht.

Wie läuft der Zertifikats-Renewal-Prozess? Betrifft uns die Verkürzung öffentlicher Zertifikatslaufzeiten (200/100/47 Tage)?

Der Renewal-Prozess hängt vom Zertifikatstyp ab. Für die HIN-Community-Kommunikation relevant sind die S/MIME-Zertifikate der HIN CA — diese haben eine Laufzeit von 12 Monaten und werden über den Tunnel zur HIN CA erneuert (siehe „Kann ich Zertifikate im Voraus erneuern?").

Zur CA/Browser-Forum-Verkürzung (ab 15.03.2026 max. 200 Tage, ab 15.03.2027 max. 100 Tage, ab 15.03.2029 max. 47 Tage): Diese Regel betrifft öffentliche TLS-Zertifikate (Server-Zertifikate von öffentlichen CAs), nicht die von der HIN CA ausgestellten S/MIME-Zertifikate. Relevant wird sie dort, wo ihr öffentlich vertrauenswürdige TLS-Zertifikate einsetzt (z.B. SMTP-TLS gegenüber Exchange Online, administrative Endpunkte). Wer dort heute lange Laufzeiten nutzt, sollte den Renewal automatisieren — bei 47-Tage-Laufzeiten ist manuelle Rotation nicht mehr praktikabel. Bei Unsicherheit, welche eurer Zertifikate betroffen sind, den konkreten Typ mit HIN klären.

Wie lade ich ein eigenes SSL-Zertifikat hoch (z.B. für TLS zu Exchange Online)?

HIN, Juni 2026 TLS-basierte Authentifizierung und verschlüsselte Kommunikation mit Exchange Online werden unterstützt. Das eigene SSL-Zertifikat lässt sich über die Web-UI hochladen.

Hinweis: Dies betrifft das eigene SSL-/TLS-Zertifikat für den Mail-Transport bzw. administrative Endpunkte. Die S/MIME-Zertifikate für die HIN-interne Mail-Kommunikation werden weiterhin ausschliesslich von der HIN CA ausgestellt — siehe „Werden externe CAs wie Let's Encrypt akzeptiert?".

(Frühere Materialien führten das als offene Frage / GitLab-Issue #342; die HIN-Antwort von Juni 2026 bestätigt den Web-UI-Upload.)

Mail-Routing & SMTP

Wie unterscheidet sich das Routing vom alten MGW?

Das Wichtigste: Im alten MGW wurde das Ziel pro Domain in der Appliance-Config eingetragen. Bei Stargate wird das im Dashboard auf /mail gepflegt — pro Domain. Standardmäßig liefert Stalwart nach DNS-MX-Lookup direkt an den Ziel-MX; alternativ kann pro Domain ein Relay (z.B. das eigene M365/Exchange-Tenant) hinterlegt werden.

Praktische Konsequenz: Domain- oder Ziel-Änderungen macht ihr im Dashboard (/mail); der mtaconf-Daemon übernimmt sie zur Laufzeit — kein Container-Neustart nötig. DNS-basiertes Routing (MX-Records) bleibt möglich, wenn ihr DNS selbst steuert.

Unterstützt der Appliance Port 587 mit SMTP-Auth (SASL)?

Teilweise Ein Relay-Ziel kann auf Port 587 zeigen, aber SMTP-SASL-Authentication ist in der Standard-Konfiguration aktuell nicht aktiviert.

Wann relevant: Wenn euer ISP outbound Port 25 blockiert (häufig bei privaten Anschlüssen und einigen Cloud-Anbietern, z.B. Azure je nach Subscription) und ihr über einen authentifizierten SMTP-Dienst wie SendGrid, Office365 SMTP-Auth oder Gmail Relay versenden müsst. Aktueller Status: in Evaluation — Bedarf mit HIN/Vereign abstimmen.

IPv6-Support?

Standardmäßig IPv4-only — Stargate setzt eine reale, statische IPv4-Adresse voraus. Hauptgrund: Microsofts Exchange-Online-Connector-GUI unterstützt kein IPv6, was zu inkonsistenter Konfiguration führt. Wer IPv6 zwingend braucht, klärt das mit HIN/Vereign.

Greylisting-Fehler (450 4.7.1) — was tun?

Das ist normal. Der Ziel-Server weist die erste Zustellung temporär zurück. Stalwart stellt nach kurzer Wartezeit automatisch erneut zu. Keine Aktion nötig.

Status/Queue: über das Dashboard (/monitoring) bzw. docker compose logs stalwart prüfen.

Microsoft blockt unsere IP (S3140-Fehler)?

Die öffentliche IP des Appliances hat schlechte Reputation bei Microsoft. Delisting beantragen unter https://sender.office.com. Dauert 24–48 Stunden. Bei häufigen Blocks IP-Warming-Strategie mit HIN besprechen.

Wie funktioniert die ausgehende Mail-Routing-Entscheidung?

Ausgehende Mails werden anhand der HIN-Maildomain-Liste entschieden (app.hin.ch/mgw/maildomains, wird alle 6 Stunden automatisch aktualisiert). Mails an HIN-Empfänger werden S/MIME-signiert und verschlüsselt versendet; Mails an externe Empfänger gehen regulär ohne S/MIME. Keine Änderung zum Legacy-MGW-Verhalten.

Unterstützt Stargate das Authenticated-Received-Chain (ARC) Protokoll?

Aktuell nein. Das neue HIN Gateway (Stargate Appliance) unterstützt ARC nicht.

Hintergrund: ARC wird relevant, wenn Mails nach dem HIN Gateway durch einen weiteren Spam-Filter laufen sollen, der die Mail auf Integrität prüft. Nach der Entschlüsselung durch Stargate ist die ursprüngliche DKIM-Signatur nicht mehr gültig — ohne ARC kann eine nachgelagerte Prüfinstanz die Authentizität der Vorhops nicht mehr nachvollziehen.

Quelle: Antwort HIN (Aroel Vanden Broele) an SRO AG, Mai 2026.

Ändert sich etwas an HIN Mail Global?

Nein — HIN Mail Global bleibt unverändert.

Kann ich Relaying auf bestimmte Systeme einschränken bzw. „Relaying allowed" konfigurieren? Wo?

Ja. Selektives Relaying — also Relay-Berechtigung nur für bestimmte Systeme statt generellem Relay für alle Exchange-Online-Server — wird über Transport-Map-Regeln im MTA abgebildet. Das ist Standard-MTA-Funktionalität und über die Web-UI konfigurierbar.

Auch die klassische „Relaying allowed"-Einstellung des Legacy-MGW lässt sich in Stargate über die Web-UI verwalten — keine manuelle Bearbeitung von Config-Files nötig.

Werden DKIM-Signaturen pro Mail-Domäne unterstützt? Lassen sich bestehende DKIM-Keys migrieren?

DKIM-Signierung pro Mail-Domäne wird unterstützt. Bestehende DKIM Private Keys, die auf dem Legacy-MGW generiert wurden, können exportiert und in Stargate importiert werden (DKIM-Key-Migration also teilweise unterstützt).

In Backlog ARC-Sealing ist aktuell nicht verfügbar und steht auf der Backlog-Liste — eine Migration vorhandener ARC-Einstellungen ist daher derzeit nicht möglich. Hintergrund zu ARC siehe Eintrag „Unterstützt Stargate das Authenticated-Received-Chain (ARC) Protokoll?".

Bleibt der HIN-Maildomain-Abruf für unsere Exchange-Transport-Rules bestehen?

Ja — der Bezug der HIN-Netzwerk-Domänen bleibt HIN-seitig bestehen. Die Maildomain-Liste (app.hin.ch/mgw/maildomains) kann weiterhin abgerufen und z.B. in Exchange-Transport-Rules importiert werden, um die Weiterleitung zum Gateway zu optimieren. Stargate selbst aktualisiert seine Domain-Liste ohnehin automatisch (alle 6 Stunden).

Netzwerk & Firewall

Muss ich wirklich eine statische öffentliche IP haben?

Ja. Die IP wird dreifach verwendet:

  • als WireGuard-Tunnel-Adresse (sie ist gleichzeitig die Peer-Identität)
  • als MXENGINE_PUBLIC_ADDRESS für Seal-Callbacks
  • als Target für eingehende SMTP-Verbindungen

Die IP zu ändern heisst: HIN muss den Peer neu registrieren, und das Zertifikat muss neu ausgestellt werden. Ohne feste IP → kein Betrieb.

NAT ist bei uns Pflicht — geht das?

Ja, aber nur 1:1-NAT mit fester IP-Zuordnung. Klassisches PAT/SNAT funktioniert nicht — eingehende Verbindungen auf Port 25, 8084 und 19818 müssen deterministisch zum Appliance durchgereicht werden. Technisch: ihr braucht eine dedizierte public IP, die auf eure interne Appliance-IP gemappt ist.

Kann ich die WireGuard-Verbindungen auf bestimmte Endpunkte einschränken (statt any↔any)?

Das any↔any ist by design. Der WireGuard-Mesh verbindet Stargate-Instanzen direkt miteinander (Peer-to-Peer), nicht nur mit der HIN-Zentrale. Der irisagent entdeckt und verbindet Peers dynamisch — also andere Stargate-Deployments bei anderen Gesundheitsorganisationen. Da diese Peer-IPs nicht im Voraus bekannt sind und sich ändern können, ist das Whitelisting konkreter Endpunkte nicht praktikabel.

Was eingeschränkt werden kann:

  • Port: nur 19818/TCP (ein Port, ein Protokoll)
  • Richtung: Inbound und outbound nur auf diesem Port

Wenn ihr nur HIN-Konnektivität braucht (keine direkte Peer-to-Peer-Kommunikation mit anderen Stargates): die HIN-Peer-Endpunkt-IP(s) lassen sich whitelisten — das würde aber Konnektivität mit zukünftigen Peers brechen.

Quelle: Antwort Vereign (Petar), Mai 2026.

Kann der Appliance mit mehreren Netzwerkkarten betrieben werden (DMZ + Management + intern)?

Ja. Der Stargate VM-Appliance ist eine Standard-Linux-VM mit Docker — mehrere NICs funktionieren ohne Probleme. In der Architektur ist nichts, was das verhindert. Die bereitgestellten VM-Images sind zwar Single-NIC, aber ihr könnt:

  • zusätzliche NICs auf Hypervisor-Ebene hinzufügen (VMware, Proxmox, Hyper-V unterstützen alle)
  • Routing so konfigurieren, dass WireGuard (Port 19818) über das DMZ-Interface geht, SMTP (Port 25) über ein anderes, Management (SSH) über intern

Die Docker-Container binden standardmäßig auf 0.0.0.0 — also kontrollieren eure OS-Routing/Firewall-Regeln, welches Interface welchen Traffic bedient. Keine Änderungen an der Stargate-Konfiguration selbst nötig.

Quelle: Antwort Vereign (Petar), Mai 2026.

Können wir Port 25 nur an unsere Firewall (z.B. Fortigate) freigeben statt direkt ans Internet?

Ja, kein Problem. Stargate ist es egal, ob SMTP-Traffic direkt aus dem Internet oder über ein Mail-Inspection-Gateway ankommt.

Voraussetzungen:

  • Die Firewall leitet die Mail unverändert an Port 25 des Stargate weiter — kein Header-Rewriting, das die S/MIME-Signaturen brechen würde.
  • Der MX-Record (oder Exchange-Connector) routet letztlich auf Port 25 des Stargate.

Das ist tatsächlich ein verbreitetes Pattern — mehrere Kunden haben ihren Stargate hinter einer Firewall bzw. einem Mail-Gateway, das Spam-Filtering durchführt, bevor es die Mail zur S/MIME-Verarbeitung an Stargate weiterreicht.

Quelle: Antwort Vereign (Petar), Mai 2026.

Welche Outbound-Destinationen muss die Firewall zulassen?

Siehe Architektur-Sektion für die vollständige Liste. Kernpunkte:

  • hub.docker.com:443 (Docker-Images)
  • *.k8s.vereign-cdn.com:443 (Sealer & CA)
  • loki.infra.vereign-cdn.com:443 (Logs)
  • vereign-issuer.vrgnservices.eu:443
  • vereign-verifier.vrgnservices.eu:4433
  • Port 25 zu allen Ziel-MX-Servern
  • DNS (Port 53)
WireGuard mit ~2.500 Domänen: brauchen wir 2.499 Knoten? Spielt HIN „Man-in-the-Middle"? Wie viel RAM?

Das WireGuard-Mesh stellt direkte Peer-to-Peer-Verbindungen her — es ist kein zentraler „Man-in-the-Middle"-Server zwischengeschaltet. Der WireGuard-Peer-Daemon unterstützt bis zu 65.536 Peers pro Interface, 2.500 Peers sind also problemlos im Rahmen.

RAM-Dimensionierung: Für 2.500 gleichzeitig aktive Peers unter voller paralleler Last werden ca. 7,5–8 GB RAM benötigt. Das sollte man einplanen, falls man wirklich mit 2.500 Peers gleichzeitig Mail/Daten austauscht. Im Normalbetrieb werden die Tunnel zu den einzelnen Peers bei Bedarf geöffnet und wieder geschlossen, wodurch der Speicherbedarf deutlich sinkt.

Peers werden dynamisch verwaltet (der irisagent entdeckt/verbindet Peers) — neue Knoten kommen automatisch hinzu, entfallene werden entfernt; keine manuelle Pflege von 2.499 Einzeleinträgen nötig.

Können wir unseren eigenen lokalen NTP-Server verwenden?

In Backlog Aktuell besteht keine Möglichkeit, den NTP-Server über die Web-UI zu konfigurieren. Diese Funktion steht auf der Backlog-Liste. Wer eine feste Vorgabe für einen lokalen NTP-Server hat, sollte den Bedarf bei HIN/Vereign anmelden und bis dahin eine Lösung auf OS-/Host-Ebene mit HIN abstimmen.

Können wir unseren eigenen lokalen DNS-Server verwenden?

In Backlog Auch die Konfiguration eines eigenen lokalen DNS-Servers steht derzeit auf der Backlog-Liste. Da Stargate für das Routing auf DNS/MX-Lookups angewiesen ist (siehe „Wie unterscheidet sich das Routing vom alten MGW?"), den konkreten Bedarf frühzeitig mit HIN/Vereign klären.

Betrieb & Wartung

Wie funktioniert das Backup?

./scripts/backup.sh läuft täglich um 02:00 automatisch (via Cron, wird beim Install eingerichtet) und erzeugt eine Tar-GZ-Datei mit:

  • Full PostgreSQL-Dump (alle 4 DBs)
  • Einzelne DB-Dumps (für Partial-Restore)
  • vault-keys.json
  • customer-config.sh
  • Alle .crt, .pem, .cer-Files
  • Manifest-JSON mit Metadaten

Retention: 7 Tage lokal in backups/. Externe Replikation müsst ihr selbst einrichten.

Wie restore ich auf einer neuen Maschine?

./scripts/restore.sh backups/YYYYMMDD_HHMMSS.tar.gz — funktioniert auf einer frischen Maschine. Das Skript:

  1. stoppt laufende Services
  2. extrahiert und validiert das Backup
  3. installiert bei Bedarf Docker
  4. restored die Customer-Config
  5. startet Infrastruktur-Services
  6. restored die Datenbanken
  7. entsiegelt Vault mit gesicherten Keys
  8. startet Anwendungs-Services

Partial-Restore einer einzelnen DB geht via psql-Import aus dem entpackten Archiv.

Vault ist nach Restart sealed — wie entsiegeln?

Einfach ./scripts/start.sh ausführen — macht die Entsiegelung automatisch mit den lokalen Keys aus secrets/vault-keys.json.

Wie funktionieren Service-Updates?

Zwei Wege:

  • Einzeln: Version in .env setzen (z.B. MXENGINE_VERSION=v0.0.31), dann docker compose pull mxengine && docker compose up -d --force-recreate mxengine
  • Alles: docker compose pull && docker compose up -d --force-recreate

Rollback: Version in .env auf vorherige setzen und erneut --force-recreate.

Nach Updates alte Images aufräumen: docker image prune -f.

Wie prüfe ich, ob alles gesund läuft?

./scripts/health-check.sh prüft:

  • alle Container-Status (running, healthy)
  • Liveness-Endpunkte der 4 Anwendungs-Services
  • Vault-Seal-Status
  • PostgreSQL-Connectivity und alle 4 DBs
  • MinIO-Health
  • WireGuard-Tunnel-Status und Peer-Handshakes
  • Stalwart (Port 25, 10026, Queue)
  • Prometheus-Endpunkte
  • Disk- und Memory-Usage

Exit 0 = alles ok. Mit -v für Details.

Wo sind die Logs zu finden?

Lokal: docker compose logs -f [service]. Zentral (falls aktiviert) in Grafana/Loki über Labels wie {environment="stargate-acme"} oder {service="mxengine"}.

Direkte Kurz-Checks:

docker logs mxengine --tail 10
docker logs irisagent | grep -i handshake
Wird Stargate weiterhin komplett über eine Web-GUI administriert wie das Legacy-MGW?

Ja. Stargate wird über eine Web-UI verwaltet, analog zum heutigen HIN-MGW. Zusätzlich lassen sich automatische, geplante Backups über die Web-UI konfigurieren. Für erweiterte Administrationsaufgaben steht zudem direkter Zugriff über die Linux-Konsole zur Verfügung.

Können wir Maillog, Authlog und GUI-Auth-Log an einen eigenen Syslog-Server (Port 514) senden?

Ja. Stargate bietet mehrere Logging-Optionen:

  • Lokale Web-UI: Logs jedes Microservice lokal im Browser unter <IP>:8090 abrufbar.
  • Externer Log-Server: Eine Remote-URL kann konfiguriert werden, um Logs an euren eigenen Syslog- bzw. Log-Aggregations-Server weiterzuleiten — z.B. Grafana Alloy, Grafana Loki oder einen beliebigen syslog-kompatiblen Endpoint auf Port 514.
  • HIN-gehostetes Log-Forwarding: Optional können Logs über einen sicheren WireGuard-Tunnel an HIN gesendet werden (Support/Troubleshooting).
Wie funktioniert ein Image-Upgrade? Bleibt die Konfiguration erhalten (neues Image statt In-Place-Update)?

Ja. Wenn statt eines In-Place-Updates ein neues Image bereitgestellt wird, lässt sich die Konfiguration über die Backup-/Restore-Funktion mitnehmen: aktuelle Konfiguration per Backup exportieren und auf der neuen Instanz wiederherstellen. Das Backup-Ziel (Speicherort bzw. Remote-Pfad) ist konfigurierbar (siehe „Wie funktioniert das Backup?" und „Wie restore ich auf einer neuen Maschine?").

Beachten: Ein vollständiger 1:1-Config-Export/-Import zwischen Legacy-MGW und Stargate wird nicht unterstützt — das betrifft nur Stargate→Stargate (siehe Migrations-Sektion).

Welche Daten werden vom alten MGW migriert?

Eigentlich keine Nutzerdaten. Stargate ist bezüglich Mail-Historie zustandslos — Mails werden verarbeitet und weitergereicht, nicht dauerhaft gespeichert. Was migriert werden muss, ist die Konfiguration:

  • Domain-Liste → im Dashboard auf /mail erfassen
  • Routing/Relay → pro Domain im Dashboard (/mail) bzw. über DNS-MX-Records
  • SPF-Records → Appliance-IP ergänzen
  • Exchange-Connectoren → auf neue Appliance-IP umkonfigurieren
Kann ich alten und neuen MGW parallel betreiben während der Migration?

Ja, bedingt. Methoden:

  • Split per Domain: Neue Domains über Stargate, alte noch über Legacy — getrennt über MX-Records.
  • Split per Empfänger-Gruppe: Transport-Rules in Exchange Online erlauben Routing bestimmter Mails über Stargate als Test.

Details zur Migrationsstrategie mit HIN-Projektleitung abklären — abhängig vom eigenen Setup.

Referenzkunden mit produktivem Stargate?

Aktuell keine — kein Kunde ist mit dem neuen Appliance in Produktion. Das ist in der Alpha-Phase erwartbar. Termin verschoben: Die für den 18.05.2026 geplante Produktions-Freigabe wurde von HIN verschoben — das Engineering-Team arbeitet noch an offenen Punkten, bevor die PRD-Images auf der Webseite verfügbar gemacht werden. Neuer Termin folgt.

Was passiert mit Mails von Legacy-MGWs während einer Zertifikats-Rotation auf Stargate-Seite?

Bestehende MGWs synchronisieren die Zertifikate ihrer Peers periodisch — aktuell alle 6 Stunden. Wenn auf Stargate-Seite ein neues Zertifikat aktiv wird und das alte invalidiert ist, kann es im Worst Case bis zu 6 Stunden dauern, bis ein Legacy-MGW das neue Zertifikat hat.

Auswirkung im Sync-Fenster:

  • Nur MGW → Stargate ist betroffen. Stargate → MGW läuft unverändert.
  • Mails, die ein noch nicht synchronisierter MGW mit dem alten Schlüssel verschlüsselt absendet, kann Stargate nicht entschlüsseln.
  • Diese Mails müssen vom Absender erneut zugestellt werden, sobald der MGW synchronisiert hat.

Was Customer-Support bei Meldung „Mail nicht angekommen" tun sollte:

  1. Prüfen, ob das Sende-Datum innerhalb von 6 h nach einer Zertifikats-Aktivierung liegt.
  2. Den Absender bitten, die Mail erneut zu senden — der MGW sollte zu diesem Zeitpunkt bereits synchronisiert sein.
  3. Falls weiterhin Probleme: HIN-Support mit Zeitstempel und Absender-MGW kontaktieren.

Geplante Mitigation: Eine Verkürzung des Sync-Intervalls mit SEPPmail wird evaluiert. Voraussetzung ist, dass alle Kunden das aktuelle MGW-Update installiert haben — in der Praxis nicht kurzfristig durchsetzbar.

Gibt es ein Standard-Migrationsszenario (Config-Export aus MGW, Import in Stargate)?

Ein vollständiger Konfigurations-Export/-Import zwischen Legacy-MGW und Stargate wird nicht unterstützt. Der von HIN empfohlene Weg in der Roll-out-Phase ist: privaten Schlüssel aus dem bestehenden MGW exportieren und beim Onboarding importieren — bei gleichbleibender IP-Adresse.

Schlüssel-Export (MGW): Im MGW-webGUI unter „Mail System" das HIN_Migration-Tool_v*.exe ausführen → „Enable export" → MGW-IP eingeben → Trusted Domain und Managed Fingerprint wählen → unter „PKCS12 download" die .p12-Datei sichern (optional mit Passwort verschlüsselt) → Export anschließend wieder deaktivieren.

Import (Stargate): Die .p12 wird während des Onboardings (Domain-Setup) importiert. Dort wird auch abgefragt, ob sec.<domain> bereits konfiguriert ist. Wichtig Wird der Schlüssel nicht beim Onboarding importiert, stellt die HIN CA ein neues S/MIME-Zertifikat aus und widerruft das alte — Mails sind dann bis zu 6 Stunden nicht entschlüsselbar (Datenverlust-Risiko).

Gleiche IP behalten: Bekommt die neue VM die gleiche IP wie die alte MGW, sind keine Änderungen am Mailserver nötig und Roll-out/Rollback bleiben einfach (Rollback = Gateway stoppen, alte MGW wieder einschalten).

Die übrige Konfiguration (Domain-Liste, Routing, SPF, Exchange-Connectoren) wird wie im Eintrag „Welche Daten werden vom alten MGW migriert?" neu aufgesetzt; DKIM Private Keys (falls auf dem MGW generiert) lassen sich ebenfalls exportieren und importieren. Den Abschluss bildet der Abnahmebericht (gateway-abnahme-de.pdf), ausgefüllt zurück an HIN.

Bleibt der Support für das Seppmail-basierte HIN-MGW 2027 erhalten, bis Stargate produktiv läuft?

HIN ist sich der Verzögerung im Projektzeitplan bewusst — und damit auch der möglichen Notwendigkeit, den Support für das seppmail-basierte HIN-MGW bis weiter ins Jahr 2027 fortzuführen. HIN prüft Migrationsfortschritt und Risiken und wird zu einem späteren Zeitpunkt entscheiden.

Empfehlung: Kunden mit Cluster-Setup (die frühestens ab September testen können) sollten eine schriftliche Zusage zum verlängerten Support-Zeitraum aktiv bei HIN einholen, statt sich auf eine mündliche Aussage zu verlassen.

Azure-VHD, VMware-OVA, Proxmox-qcow2, Hyper-V-Image, Docker auf bestehendem Host, oder Kubernetes-Helm.
SSH-Zugriff für Betriebsteam eingerichtet
Wer darf auf den Appliance? 2-Personen-Regel oder privilegiertes Betriebs-Konto.
Backup-Zielort definiert
Externer Storage für tägliche Replikation des backups/- und secrets/-Verzeichnisses. Ohne externes Backup ist bei Totalverlust alles weg.

2 · Firewall-Freischaltungen · Netzwerk-Team

Ein häufiger Stolperstein, besonders 19818 in beide Richtungen.

Inbound (vom Internet zum Appliance):

Port 25/TCP — SMTP (Mail-Empfang von extern)
Port 8084/TCP — HTTP Seal-Callback
Für Remote-Sealer von der HIN-Seite. http:// ist korrekt — TLS nicht nötig, weil das Seal-Payload bereits verschlüsselt ist.
Port 19818/TCP und UDP — WireGuard
Beide Protokolle, auch wenn ihr nur TCP-Mode nutzt — erleichtert später Switch zu UDP falls nötig.

Outbound (vom Appliance ins Internet):

hub.docker.com:443
Docker-Image-Registry.
mxengine-dev.k8s.vereign-cdn.com:443
smimekeys-ca-dev.k8s.vereign-cdn.com:443
loki.infra.vereign-cdn.com:443
Nur wenn zentrales Logging aktiv. Sonst Regel trotzdem anlegen für Support-Cases.
vereign-issuer.vrgnservices.eu:443
vereign-verifier.vrgnservices.eu:4433
Port 25/TCP zu beliebigen Destination-MX-Servern
Viele Corp-Firewalls blockieren outbound 25 standardmässig — explizit freischalten.
DNS (Port 53) — UDP und TCP
Pflicht für MX-, SPF- und A-Record-Lookups.

3 · DNS-Vorbereitung · DNS-Team

DNS-Records müssen vor dem Go-Live stehen, wegen TTL-Propagation.
A-Record für Mail-Hostname
mail.<domain>. A <SERVER_STATIC_IP>
MX-Records pro Domain gesetzt
Für jede Domain: Exchange mit niedriger Priorität (z.B. 10), Stargate mit höherer Priorität (z.B. 20) — sonst hat Stargate kein Auslieferungsziel.
SPF-Record um Appliance-IP erweitert
Pro Domain: bestehendes v=spf1 …-Record um ip4:<SERVER_STATIC_IP> ergänzen. Sonst SPF-Fails bei ausgehender Mail.
Reverse-DNS (PTR) gesetzt
Die Appliance-IP sollte rückwärts auf mail.<domain> auflösen. Verbessert Reputation bei Microsoft und anderen grossen Providern.
TTLs vor Go-Live auf niedrige Werte (5 Min) gesetzt
Erleichtert Rollback. Nach erfolgreichem Go-Live auf produktive Werte zurücksetzen.
DNS-Records verifiziert
Mit host -t mx <domain>, host -t txt <domain>, host <mail-hostname>.

4 · Installation

Die eigentlichen 30 Minuten.
customer-config.sh vorbereitet
Aus customer-config.example manuell abgeleitet und an die eigene Umgebung angepasst.
./scripts/install.sh erfolgreich durchgelaufen
Dauert 5–10 Minuten. Installiert Docker bei Bedarf, startet Stack, initialisiert Vault, führt initiales Onboarding aus.
Alle Container laufen healthy
docker ps --format 'table {{.Names}}\t{{.Status}}' zeigt keine restarts.
./scripts/health-check.sh läuft grün
Alles ausser Zertifikat und WireGuard-Handshake sollte ok sein — die kommen nach Peer-Registrierung.
Secrets-Backup-Verzeichnis extern gesichert
secrets/vault-keys.json und customer-config.sh (mit auto-generiertem WG-Private-Key) mindestens auf einen anderen Storage kopiert.

5 · Peer-Registrierung bei HIN · kritischer Schritt

Ohne diesen Schritt kein Zertifikat. Betrifft jeden Rollout.
WireGuard-Public-Key aus irisagent-Logs ausgelesen
docker compose logs irisagent | grep "public key"
E-Mail an HIN versendet
Enthält WG-Public-Key, DEPLOYMENT_NAME, SERVER_STATIC_IP, bei abweichendem Port auch WG_INTERFACE_PORT.
Bestätigung von HIN erhalten
Zertifikat-Regenerierung ausgeführt
Im Dashboard auf /onboarding das Zertifikat anfordern
WireGuard-Handshake bestätigt
docker exec irisagent wg show zeigt latest handshake: < 2 min ago.
S/MIME-Zertifikat in smimekeys-client sichtbar
docker logs stargate-smimekeys-client | grep -i "certificate" — Issuer sollte HIN Test CA (bzw. HIN CA in Produktion) sein.

6 · Exchange-Integration · Mail-Team

Setup im Exchange-System (M365 oder on-prem).
Outbound-Connector erstellt
Exchange → Stargate, Smart-Host = SERVER_STATIC_IP, nur via Transport-Rule getriggert.
Inbound-Connector erstellt
Stargate → Exchange, IP-basierte Authentifizierung mit SERVER_STATIC_IP.
Transport-Rule angelegt und aktiviert
Rule wird im Disabled-Zustand erstellt — aktivieren nicht vergessen.
IP-Exception in der Transport-Rule gesetzt
Except if sender IP is <SERVER_STATIC_IP> — verhindert Mail-Loops. Häufig vergessen, immer prüfen.
Connector-Validierung erfolgreich
Im Exchange-Admin-Center den Validate-Button mit einer echten Empfängeradresse geklickt.

7 · Funktionstests

Bevor der Rollout produktiv geht, Testmails durchlaufen lassen.
Testmail extern → intern erfolgreich
Von einer externen Adresse (z.B. Gmail, Web.de) an eine interne Adresse — sollte via Stargate ins Postfach kommen.
Testmail intern → extern erfolgreich
Aus Outlook an externe Adresse — sollte via Stargate relayt werden, SPF-Check beim Empfänger muss bestehen.
Testmail intern → HIN-Empfänger (S/MIME)
An eine HIN-Empfängeradresse — sollte signiert und verschlüsselt durchgehen.
Keine Mail-Loops in Exchange-Trace
Im Exchange-Message-Trace keine Mails mit mehreren Weiterleitungen an Stargate-IP sichtbar.
Queue leer
docker compose logs stalwart zeigt keine hängenden Mails.

8 · Betriebs-Übergabe

Bevor ihr das System an den regulären Betrieb übergebt.
Monitoring angebunden
Prometheus-Scraping auf Ports :2113/:2114/:2115/:2116/:9100 konfiguriert. Mindest-Alerts: Container down, Zertifikat-Ablauf < 30 Tage, Queue > 100 Mails, WireGuard-Handshake älter als 10 Minuten.
Backup-Cronjob verifiziert
crontab -l zeigt den 02:00-Job, ein manueller Testlauf erzeugt ein Backup-Archiv.
Externe Backup-Replikation läuft
Nach 24 h: Backup-Archiv von gestern ist im externen Storage angekommen.
Restore-Test auf Stage-VM durchgeführt
Einmalig das Backup auf einer frischen VM mit ./scripts/restore.sh einspielen — um zu beweisen, dass es wirklich funktioniert. Ohne Test ist ein Backup kein Backup.
Runbook an Betriebsteam übergeben
Dokumentiert: SSH-Zugang, Start/Stop, Update-Prozess, Monitoring-Dashboards, Eskalations-Kontakt bei HIN.
2nd-Level-Kontakt bei HIN dokumentiert
Name, Mail, Telefonnummer, SLA.
